Course path · 10 blocks · Brian Olliff
01

Threat Hunting Overview

  1. 1.1

    What is Threat Hunting?
    • Proactively looking for threats in infrastructure using logs from endpoints, network devices, authentication systems, etc.
    • Proactive vs reactive:
      • Reactive — alerts from EDR, SOC, SIEM, IPS, etc.
      • Proactive — searching through logs for indicators of compromise.
      • Reactive methods are insufficient for advanced threats.
    • Uses "assumption of breach."
    • Does not replace alert-based detections — it's part of defense-in-depth.
  2. 1.2

    Assume Breach
    • Investigating and analyzing while assuming a threat actor is on the network.
    • Requires many other assumptions and hypotheses:
      • System that may be compromised
      • How the system may be compromised
      • Threat actor involved (adversary TTPs)
    • Not necessarily reacting to any threat or alert.
  3. 1.3

    Threat Hunting vs. Incident Response
    • Threat hunting ≠ incident response.
      • TH is a passive activity.
      • IR is an active activity.
    • Threat hunters and incident responders work closely together:
      • Hunters discover threats and relay information to responders.
      • Responders often gather additional information to provide to hunters — hash values, memory dumps, disk images, file contents, etc. — plus additional indicators for new threat hunts.
    • Responding to threats alters data on systems — could affect an in-progress hunt.

    Where TH fits alongside adjacent disciplines (proactive vs reactive):

    DisciplinePostureUses
    Threat HuntingProactiveManual analysis; intelligence information; TTPs
    Vulnerability ManagementProactiveVulnerability feeds; automation & orchestration
    Incident ResponseReactiveData analytics; automation
  4. 1.4

    Threat Hunting Goals
    • Detect advanced threats in infrastructure — "routine/common" threats are often detected by monitoring, but advanced threats need proactive hunting:
      • Nation-state actors
      • Insider threats
      • New/advanced malware
    • Reduce time that attackers are in the network:
      • Attempt to identify threats in early stages.
      • Less time to cause damage, exfiltrate data, etc.
02

Why Threat Hunting Matters

  1. 2.1

    Dwell Time
    • Dwell time = amount of time an adversary is on the network undetected and retains access.
      • Time to gather/exfiltrate data, collect credentials, lateral movement / privilege escalation, deploy other tools.
    • Impacted by multiple factors:
      • Detection of intrusion before goals achieved.
      • Attacker achieves their goal(s), or detonates a "noisy" payload.
    • Mandiant report benchmarks: 2022 — 16 days. 2023 — 10 days.
  2. 2.2

    AV / EDR Limitations
    • Systems work based off pre-determined detection rules:
      • Signatures
      • User behavior
      • File hashes / filenames
    • If an attack doesn't match a rule, the security control isn't aware — no alerts or actions if the detection rule isn't triggered.
    • Requires constant updating for awareness of new malware / attacks / tools.
    • Should still be used, but will not detect all threats.
  3. 2.3

    Better Defenses (Byproducts of Hunting)

    Threat hunting can discover many other security issues:

    • Priority vulnerabilities that need remediation
    • Misconfigurations on endpoints
    • Unapproved software on workstations
    • Access issues

    All data found during a hunt can be used to improve the security of the organization:

    • Adjustments of security controls
    • New security controls that need to be implemented
    • Improvements to logging infrastructure
    • Additional signatures / rules for detection systems
  4. 2.4

    When to Hunt
    • Orgs with threat hunting teams often have scheduled hunts — routinely performed based on various hypotheses.
    • New intelligence received about a potential threat:
      • Attacks against similar organizations / same industry.
      • Actively exploited vulnerabilities in software / systems the org uses.
    • SOC / IR teams report an incident:
      • Active incident that requires additional hunting.
      • Anomalous activity on the network.
    • Additional IOCs identified as part of a previous hunt.
    • After completion of a risk assessment — verify riskiest assets / systems are secure.
03

Threat Hunting Strategies

  1. 3.1

    Phases of Threat Hunting

    1. Trigger

      Reason for the hunt, usually in the form of a hypothesis.

    2. Investigation

      Using the hypothesis, search data for supporting evidence. The hypothesis may be adjusted during the hunt, based on evidence found.

    3. Resolution / Outcome

      What was the outcome of the hunt? Hypothesis true? Communication and reporting of information. May pivot into a new hunt.

    Loop diagram from the deck: Threat Hunting → Trigger → Investigate & Analyze → Outcome → Refine Tactics → Reveal New Info → back to Threat Hunting.

  2. 3.2

    Types of Hunts
    • Structured
      • Begins with searching for specific TTPs.
      • Hypothesis based on the attacker's method.
      • Hunt based on possible symptoms of that type of attack.
    • Unstructured
      • Typically starts with IOCs and searching logs for them.
    • Situational
      • Focused on specific resources or systems in the organization.
      • Often starts with a risk assessment — hunt based on those findings.
04

Threat Hunting Terminology

  1. 4.1

    Threat
    • Any potential negative impact (or danger) to an asset — any item owned by an individual or organization.
    • Threat actor — entity taking advantage of a vulnerability / risk.
    • Threat / attack vector — path used to perform an attack.
    • Types of threats:
      • Natural disasters
      • Virus / malware
      • Data breach
      • Denial of service (DoS)
      • APTs
  2. 4.2

    APT (Advanced Persistent Threat)
    • Used to refer to groups or types of malware.
    • Attacker group with significant resources, infrastructure, and capabilities:
      • Long-term detection evasion.
      • Multi-stage attacks.
      • Quick use of zero-days.
      • Custom zero-days.
    • Different naming conventions used by different vendors:
      • APT / UNC / FIN# — e.g. APT29 (Mandiant / Google).
      • Animal names — e.g. Cozy Bear (CrowdStrike).
      • Weather events — e.g. Midnight Blizzard (Microsoft).
    • Reference: https://attack.mitre.org/groups/G0016/
  3. 4.3

    TTPs (Tactics, Techniques, and Procedures)
    • Methods or patterns used by threat actors.
    • Tactics — high-level description of behaviors and strategies.
    • Techniques — more specific methods describing how tactics can be implemented.
    • Procedures — sequence of activities using specific techniques to carry out attacks; can be tailored for different threat actors / groups.
  4. 4.4

    IOCs and Hashes
    • Indicators of Compromise — artifacts that may indicate presence of malicious activity:
      • File hash, IP address, domain name, filename, strings, etc.
      • Behavioral & other anomalous activity.
      • Included in threat intelligence reports.
    • Hashes:
      • Unique value that represents the "digital fingerprint" of a file.
      • Generated by running the file through a hashing algorithm.
      • Common: MD5, SHA256 / SHA512, etc.
05

Pyramid of Pain (David Bianco)

  1. 5.1

    Overview

    Created by David Bianco. Shows the difficulty in obtaining different IOCs — and also the level of effort for an attacker to change them. The pyramid, from base (trivial) to apex (most painful):

    1. Hash Values

      Bottom of the pyramid — trivial for attackers.

    2. IP Addresses

    3. Domain Names

    4. Network / Host Artifacts

    5. Tools

    6. TTPs

      Apex — most painful for adversaries.

  2. 5.2

    Hash Values
    • Very easy to discover and use.
    • No question of compromise if one is found.
    • Trivial for an attacker to change — any change to a file results in a completely different hash.
  3. 5.3

    IP Addresses
    • One of the most fundamental indicators.
    • If a malicious IP is found — near certainty of malicious activity.
    • Very easy for an attacker to change, especially if using domain names.
    • Many attackers use "temporary" IPs.
  4. 5.4

    Domain Names
    • Similar type of IOC as IPs.
    • More difficult for an attacker to change — requires:
      • Registration
      • Payment
      • Hosting
    • May be delay in propagation.
  5. 5.5

    Network & Host Artifacts
    • User-agent strings.
    • Traffic on non-traditional ports.
    • Specific file / registry key.
    • Non-browser process on port 80/443.
    • Often requires the attacker to reconfigure or recompile.
  6. 5.6

    Tools
    • APT groups tend to use a consistent set of tools.
    • Requires detection of specific artifacts of unique tools.
    • Blocking specific tools requires adversaries to find / create new tools for the same purpose.
  7. 5.7

    TTPs (Apex)
    • Attacker's training, methods.
    • Detecting adversary behavior, not their tools.
    • If responding quickly, may force attackers to learn new behaviors.
06

Cyber Kill Chain (Lockheed Martin)

  1. 6.1

    The 7 Stages

    Reference: https://www.lockheedmartin.com/en-us/capabilities/cyber/cyber-kill-chain.html

    1. Reconnaissance

      Attacker gathers information about target. Passive and active methods: internet searches, email harvesting, network scans.

    2. Weaponization

      Attacker creates deliverable payload. May consist of a Remote Access Tool (RAT) or other backdoor, encryption tools, or another malware downloader.

    3. Delivery

      Malicious payload sent to victim — email, watering hole attack (malicious website), drive-by download, malicious USB drive.

    4. Exploitation

      Malicious payload is run on the victim system — user opens email attachment, or visits a malicious website where malware downloads/runs. Attacker may exploit other vulnerabilities using other methods. Can be a multi-step process: original payload runs and downloads additional malware.

    5. Installation

      Additional tools installed via original RAT / backdoor — encryption software, more complex malware, command & control software, exfiltration tools. Any tools the attacker needs to carry out the objective.

    6. Command & Control (C&C)

      Victim machine connects to attacker-controlled infrastructure. May use well-known ports to evade firewall rules / detection. Traffic may be encrypted. Allows additional commands and malware to be run — attacker can further customize based on victim environment.

    7. Actions on Objectives

      Attacker accomplishes original goals based on all previous steps: encryption and ransom demand; data theft (and possible ransom); destruction of data or systems; software disruption; persistent access for further goals.

Organization Preparation

  1. 8.1

    The Preparation Wheel

    Preparation for threat hunting has five sides:

    • Threat Hunting Personnel
    • Data Collection
    • Aggregation & Analysis Tools
    • Appropriate Access
    • Threat Intelligence
  2. 8.2

    Threat Hunting Teams

    Not necessarily a standard definition of a team — based on size of org, industry, systems, etc.

    • Ad-hoc hunter
      • Typically has multiple roles in IT / security.
      • Hunts are more "task-oriented."
    • Analyst and hunter
      • Most common in medium-sized organizations.
      • Security (SOC) analyst is also the threat hunter.
    • Dedicated hunting team
      • Most specialized.
      • Several members whose sole purpose is threat hunting.
  3. 8.3

    Software and Systems
    • Threat hunting requires data to be collected prior to the hunt.
    • Logs from multiple systems ingested into a central point (SIEM) — also provides a point for searching logs from multiple systems. Examples: Splunk & ELK stack.
    • Packet capture and analysis — Wireshark.
    • EDR systems — provide additional data that may not be included in other logs.
    • Threat intelligence information — data feeds, in-house team, third-party vendor.
  4. 8.4

    Log Preparation
    • Ensure appropriate logs are being collected and saved — endpoints, servers, network devices, authentication systems, cloud, apps, etc.
    • Log retention
      • Logs must be kept for an appropriate amount of time.
      • Retention length varies by organization.
      • May require a large amount of storage.
      • More logs = less retention (with equal amount of storage).
    • May need additional software for more detailed logs — e.g. Sysmon (MS Sysinternals).
  5. 8.5

    Infrastructure Logging — What To Log
    • Account and group activity
      • Creation, deletion, modification.
      • Log on/off — including source information.
    • Network traffic & devices
      • Firewall traffic — inbound and outbound.
      • Internal network traffic as needed.
    • File activity
      • Especially any sensitive, proprietary information.
      • File creation, modification, deletion.
    • Email systems
      • Any email filtering.
      • Inbound and outbound mail.
    • Endpoint event logs
      • Windows systems — PowerShell, system, application, Sysmon.
    • Applications — any specific application logs that may be relevant to security.
    • Any public-facing interfaces
      • Web servers
      • Remote access gateways
      • Email portals
      • Customer interface
      • APIs
  6. 8.6

    Baselines & Known Good Configurations
    • Measure of what is "normal" on an endpoint / network:
      • File hashes
      • Open network ports
      • Accounts on endpoint / permissions granted
      • File / directory permissions
    • Used to compare against current state:
      • If matches baseline — proceed.
      • If does not match baseline — further investigation to determine why and if malicious.

10

Threat Hunting Mindsets

  1. 10.1

    Intelligence-Based Hunting
    • Hypothesis to begin hunt starts with intelligence information — IPs, domains, hashes, filenames, email addresses, other IOCs.
    • Strategic: Who?, Why?, and Where?
    • Tactical: What? and When?
    • Operational: How?
  2. 10.2

    Data-Driven Hunting
    • Driven mainly by internal data that may indicate malicious activity:
      • Lower priority alerts.
      • Detections based solely on aggregated data.
    • Does not typically start with a definite "something bad is happening" — provides a potential starting point to create a hypothesis.
    • Still uses intelligence information.
  3. 10.3

    Knowledge-Based Hunts
    • Relies more on the hunter's knowledge of available data:
      • Logs and events.
      • Network layout and architecture.
      • Adversary TTPs.
    • Heavily uses frameworks (MITRE ATT&CK).
    • Hypothesis created based on TTPs seen in the wild — knowledge of TTPs helps to know how to look for suspicious activity.
  4. 10.4

    Attack-Based vs Analytics-Based
    • Attack-based hunting
      • Searching for evidence whether or not an attack has occurred.
      • "Did <event> occur on the network?"
    • Analytics-based hunting
      • "Does anything in <system / network / data> look malicious or suspicious?"

The Role of Threat Intelligence in Cybersecurity

  1. 1.1

    What is Threat Intelligence?

    Threat intelligence is built from: Indicators of Compromise (IoCs), Tactics, Techniques, and Procedures (TTPs), Attribution Information, and Contextual Data.

    CTI across the Cyber Defense Lifecycle (Planning → Prevention → Detection → Response → Recovery, a continuous cycle):

    • Planning: vulnerability prioritization, policy hardening, threat modeling, blacklisting (disallow listing).
    • Prevention: (feeds into the same cycle, informed by planning).
    • Detection: IOC matching, TTP detection, alert enrichment, threat hunting guides.
    • Response: adversary playbooks, contextual response, attribution support.
    • Recovery: post-incident review, lessons learned, improvement planning.

    The cycle is also fed by planning-level activities: risk assessments, security roadmaps, simulations/tabletop exercises, regulatory compliance.

    Benefits of CTI: reduces breach costs, speeds up detection and response, improves SOC efficiency, enables proactive defense, and has direct real-world relevance.

  2. 1.2

    Where CTI Fits & Why It's Needed

    Where threat intelligence integrates into existing infrastructure: SIEM, Endpoint Detection and Response, Firewall/WAF, SOAR, and dedicated Threat Intelligence Platforms.

    Sources: OSINT, government feeds (e.g., CISA KEV, NVD), ISACs, commercial feeds, dark web monitoring.

    What good CTI delivers: faster incident response, reduced risk exposure, better investment decisions, more effective threat hunting.

    Common CTI failure modes: information overload, poor relevance to the organization, lack of trained analysts, and failure to operationalize the intelligence collected.

    CTI as a force multiplier: it adds value across the entire Cyber Defense Lifecycle — the mantra is "Don't just collect — operationalize" and "Quality over quantity." It requires people, process, and technology together, not any one alone.

03

Core CTI Processes

  1. 3.1

    The CTI Lifecycle

    An iterative cycle where each phase builds on the last, with actionable intelligence as the goal: Planning & Direction → Collection → Processing & Exploitation → Analysis & Production → Dissemination → Feedback (which loops back to Planning & Direction).

    Applied specifically to threat hunting, each stage looks like:

    1. Planning & Direction — Define the Hunt

      What threats matter to us now? Who are we hunting and why? What are our Priority Intelligence Requirements (PIRs)? Which MITRE TTPs should we focus on? Example: "We've seen TA577 abusing DLL search order hijacking in our sector. Let's hunt for T1574.001 across legacy systems."

    2. Collection — Gather the Right Telemetry

      Pull EDR, NetFlow, Windows Logs, Authentication Logs; integrate CTI (IOCs, TTPs, actor profiles); align with hunt scope and assets. Example: "Collected DNS logs after CTI warned of APT28 using 'cdn-assets-update[.]com'."

    3. Processing & Exploitation — Normalize and Enrich Data

      Normalize logs into a common format; de-dupe and filter irrelevant data; enrich with context (GeoIP, WHOIS, MITRE tags). Example: "Used a script to tag base64 PowerShell commands with T1059.001 and flag unsigned scripts."

    4. Analysis & Production — Test the Hypothesis

      Look for anomalous behavior; correlate events across systems; validate adversary TTPs in the environment; document findings with context and severity. Example: "Lateral movement via PSExec discovered after matching IR evidence to Lazarus TTPs."

    5. Dissemination — Get the Intel to the Right Hands

      Alert the SOC for detection engineering; share with IR and leadership; document in knowledgebases or playbooks. Example: "IOC list delivered to firewall team; Sigma rule deployed in SIEM to catch reuse."

    6. Feedback — Improve the Next Hunt

      Review what worked/didn't; collect feedback from IR/SOC/CTI teams; update PIRs, scope, and detection logic. Example: "SOC reported false positives on the PowerShell rule; we refined it using baseline logic."

  2. 3.2

    Prioritizing Intelligence

    Why prioritization matters: you can't act on everything (the flood of intel); wasted effort vs. focused response (the cost of distraction); the goal is Relevance + Urgency + Impact.

    The three-way balance — Relevance, Actionability, Criticality:

    • Relevance — Is it aligned with your industry, assets, geography, threat model? Example table: an indicator seen in the Financial sector using Citrix, Asia-only, scores Medium relevance; one seen in Healthcare on Microsoft 365, US-based, scores Low relevance.
    • Actionability — Can it be used to inform detection/prevention? Actionable indicators include IPs/domains with rich context (first seen, campaign link, threat actor), TTPs tied to detections in your EDR/SIEM, and Snort/YARA/Sigma-format rules.
    • Criticality — What is the risk if left unmitigated? Factors: potential impact (financial, operational, reputational), data at risk, threat actor sophistication. Risk = Likelihood × Impact.

    Scoring frameworks:

    • Admiralty Code (NATO rating system) — rates Source Reliability (A–F) and Information Credibility (1–6) for incoming intel.
    • Diamond Model — evaluates Adversary, Infrastructure, Victim, and Capability, scored by proximity to your assets/operations.
    • Risk-Based Scoring — formula: Likelihood × Impact × Exposure, ties intelligence directly to risk posture.

    Prioritization matrix (Relevance × Actionability): Low Relevance + Low Actionability → Ignore. Low Relevance + High Actionability → Watch. High Relevance + Low Actionability → Investigate. High Relevance + High Actionability → PRIORITIZE.

    Automation vs. the analyst: SIEMs and TIPs can automate prioritization (STIX tags, scoring feeds, expiration dates), but analysts are still needed for campaign tie-ins, understanding nuanced TTPs, and applying internal organizational knowledge.

    Key takeaways: not all intelligence is equal; prioritize based on Relevance, Actionability, and Criticality; use scoring frameworks to stay consistent; human analysis adds needed nuance.

  3. 3.3

    CTI Lifecycle Case Study — Ransomware on a Healthcare Provider

    Scenario: January 2024; threat actor suspected APT28-affiliated; impact — critical systems locked, patient data encrypted.

    Walking the full lifecycle against this scenario:

    • Planning & Direction: driven by CISO, Threat Intel Lead, Incident Commander, focused on identifying what needs to be known (IoCs, threat actor TTPs, infrastructure at risk). Example: "Determine if this is part of a broader campaign targeting the health sector."
    • Collection: internal (logs, SIEM events, EDR telemetry) and external (OSINT, ISAC reports, CTI vendors, dark web).
    • Processing & Exploitation: normalize data (timestamps, IPs, domain names, log formats), de-duplicate, enrich with GeoIP/WHOIS/MITRE mappings — moving Raw Logs → Parsed → Enriched.
    • Analysis & Production: answers what's happening, who's behind it, what the objective is, and how to stop it. Example output: threat actor profile, IOC set, kill chain stage.
    • Dissemination: formats include a flash report, threat bulletin, briefing, or Slack/ticket system, reaching SOC/Detection Engineers, Incident Response, Executive Leadership, Legal and Compliance, Threat Sharing Groups, and External Partners — all coordinated through the Threat Intelligence Team.
    • Feedback: did the intel help detection or response? Were there gaps in collection? What should be done differently next time?

    Roles by stage:

    StageTypical roles involved
    DirectionCISO, IR Lead, CTI Lead
    CollectionCTI Analysts, Threat Hunters
    Processing & ExploitationAutomation Engineers, Intel Techs
    Analysis & ProductionIntel Analysts, Hunt Team
    DisseminationCTI Lead, Report Writers
    FeedbackAll Stakeholders

    Outputs by level, from this same case: Tactical — enriching SOC alerts, blocking malicious IPs; Operational — campaign tracking, adversary TTP monitoring; Strategic — budgeting, long-term security priorities.

    Key takeaways: the intelligence cycle is iterative and flexible; direction and feedback are crucial bookends; real-world ops require fast but accurate intelligence flows; integrating the cycle into IR and detection makes teams proactive.

  4. 3.4

    Adversary Analysis & MITRE ATT&CK

    Adversary analysis = tracking, profiling, and understanding threat actors. MITRE ATT&CK is a knowledgebase of tactics and techniques observed in the real world, mapping the observed behaviors of known threat actors or campaigns across a tactic chain (Initial Access → Privilege Escalation → Defense Evasion → Lateral Movement → Collection → Exfiltration).

    ATT&CK stands for Adversarial Tactics, Techniques, and Common Knowledge, and is structured as:

    • Tactics — the adversary's goals.
    • Techniques/Sub-techniques — how the goals are achieved.
    • Mitigations and relationships — how to respond.
    • Data sources and detections — which logs/signals can detect the behaviors.

    How analysts use ATT&CK: map threat-group behavior, compare behaviors across incidents, hunt for activity using TTPs, and prioritize detection engineering. Threat Actor pages list known techniques, tools, software, and references.

    Working from indicators: e.g., use of PowerShell (T1059.001) or use of Web Protocols (T1071.001) — asking "does this activity match other known threat actor activity?" to guide incident response and assess adversary objectives.

    ATT&CK is not a silver bullet — it maps behaviors, not just indicators. Core use cases: Threat Hunting, Detection Engineering, Threat Emulation/Red Teaming, and Attribution Support.

  5. 3.5

    Correlating Indicators of Compromise

    Correlation links IoCs across time, tools, and sources — transforming isolated data points into an intelligence picture, and enabling detection, attribution, and response.

    IoCs are digital clues tied to malicious activity — can be atomic (an IP, a hash value) or behavioral (a process tree) — used to detect, track, and stop threats.

    Sources for correlation: internal telemetry (SIEM, EDR, DNS, proxy), external intel (MISP, OSINT, vendor feeds), government/ISACs (CISA, sector-specific ISACs), historical incidents and ticketing systems.

    Why correlate: validate threats using multiple sources; enhance context and actor attribution; detect low-signal or stealthy threats; link infrastructure and uncover campaigns.

    Five correlation techniques:

    1. Exact Matching

      Direct one-to-one matching of identical IOC values (IPs, hashes, domains) across datasets; the most basic form, often automated in SIEMs/TIPs/feeds. Example: IP 192.0.2.45 seen in both the org's SIEM and a subscribed threat intel feed.

    2. Infrastructure Pivoting

      Using one IoC to discover related indicators via shared infrastructure (pivot from a domain to its IP, then find all domains on that IP; uses WHOIS, passive DNS, SSL cert reuse, ASN data) to expand visibility into the adversary's digital footprint. Example: domain evil-login[.]net hosted on 45.66.123.9, which also hosts 5 other known malicious domains.

    3. Fuzzy Matching

      Identifying indicators that are similar but not exact (typosquatting/lookalike domains, fuzzy hashing like ssdeep for near-identical malware, minor code/filename variations). Example: dropbox[.]com vs. dropb0x-secure[.]com; malware hashes with 93% similarity.

    4. Time-Based Analysis

      Correlating IoCs by event timing to reconstruct incidents, linking events across logs by timestamp to reveal attack progression and lateral movement, supporting timeline-based hunting/IR. Worked example — a single incident reconstructed from a phishing email hash at 10:03 AM, a matching DNS lookup at 10:05, an obfuscated PowerShell process at 10:06, and an outbound C2 connection at 10:07, all correlated together.

    5. TTP and Campaign Linking

      Matching IoCs to known tactics, techniques, and threat-actor patterns: aligning IoCs with MITRE ATT&CK techniques, identifying repeat tool sets/scripting behaviors, mapping to historical campaigns/APT profiles. Examples: a PowerShell command mapping to T1059.001; infrastructure overlap confirming behavioral linkage to an APT28 campaign.

    Tools: TIPs (threat sharing and event correlation), MITRE ATT&CK Navigator, Maltego (infrastructure graphing), Elastic/Splunk (internal log correlation), Python scripts plus enrichment APIs.

    Best practices: normalize and enrich data before correlating; use STIX/TAXII for standardization; always verify external IoCs against internal logs; tag by time, actor, and confidence; avoid correlation overload (don't link everything).

    Key takeaways: IoCs are valuable alone, but powerful when linked; correlation reveals intent, infrastructure, and actor behavior; use tools and context to go beyond surface indicators; good correlation is the difference between alerts and insight.

04

Integrating CTI into Detection & Defense

  1. 4.1

    CTI-Driven Detection Engineering

    Benefits: faster detection of known-bad, improved context for analysis, better alert triage with fewer false positives, and automation possibilities.

    Feed sources: Open Source/OSINT (AlienVault OTX, Abuse.ch), Commercial (Recorded Future, ThreatConnect), ISACs/Government (FS-ISAC, CISA), Internal (honeypots, IR reports).

    Pipeline: Collection → TIP → SIEM. SIEM enrichment adds CTI data to raw logs; detection logic triggers alerts on IOC/TTP matches; SOAR uses CTI to prioritize and automate the response.

    IOC-based detection: IP/URL/hash matching, GeoIP & ASN-based risk scoring, expiry- and context-based IOC filtering.
    TTP-based detection: ATT&CK-aligned rules (e.g., detecting credential dumping), threat behaviors tied to known adversaries, mapping detection coverage to ATT&CK.

    Before/after example — moving from static to context-aware detection:

    • Before: IF src_ip == x.x.x.x THEN alert
    • After: IF src_ip IN [Threat Feed] AND Threat_Level >= 7 AND NOT PreviouslySeen THEN alert with context

    SOAR's role: enrich alerts with threat actor data, automate blocking in the firewall, prioritize incidents based on threat scoring.

    Success metrics: reduction in false positives, Mean Time to Detection (MTTD), coverage of known threats, analyst feedback.

    Common pitfalls: too much noise from low-quality feeds, stale IoCs, over-reliance on atomic indicators, poor correlation with the local environment.

    Best practices: use vetted, high-confidence feeds; apply context (malware family, campaign); regularly tune detection rules; automate IoC expiration; feed CTI back from IR teams (closed loops).

    5-stage CTI maturity model: Ad hoc CTI lookup → IoC ingestion into SIEM → Detection rule tuning → Behavioral analytics → Full SOAR-based response.

    Key takeaways: integration is key to making CTI actionable; SIEMs benefit from high-quality intel plus context; automation supercharges response; CTI is not just IoC matching — think behavior, context, threat actor.

  2. 4.2

    IoC Enrichment & Contextualization

    Common challenges without enrichment: lack of context, high false positives, no prioritization, blind spots in response.

    The enrichment wheel around an IoC: WHOIS (registrant, creation date), Passive DNS (historic domains), Related hashes and malware families, Reputational Data (VirusTotal score), GeoIP (country, ISP).

    Contextualizing questions: Is this part of a known campaign? What stage of the attack does it relate to? Does this affect my industry?

    Worked example: a SOC alert fires for outbound traffic to 34.117.59.81. Enrichment reveals: WHOIS shows it belongs to Google Cloud; GreyNoise shows it scanning SSH globally; VirusTotal flags it malicious in 3 engines; Passive DNS shows it previously resolved from akudate.evilcorp[.]com; sandbox analysis shows it dropped an Emotet payload. Contextualizing all of that together: this is likely C2 infrastructure, previously used by an Emotet variant, seen in phishing campaigns in the past 7 days, and associated with TTPs linked to TA542.

    Pipeline: IoC → Enrichment Layer → Context Layer → Outputs (Detection Engineering, Threat Hunting, Reporting/Intel Feeds, Incident Response).

    Sources: Internal (SIEM, IR logs, sandbox detonation); External (VirusTotal, PassiveTotal, MISP, AbuseIPDB, AlienVault OTX, Shodan).

    Mapping ATT&CK tactics to IoC types:

    Cautions: reputation doesn't equal attribution; shared infrastructure ≠ shared actor; data staleness is real (last seen ≠ still active).

    Role-specific use: SOC Analyst — enriched IoCs drive correlation rules; Threat Hunter — uses context to guide hypothesis-driven hunts; CTI Analyst — adds actor info and ATT&CK mapping for reporting.

    Core idea: Enrichment = data about the IoC. Contextualization = meaning around the IoC. Together = actionable intelligence.

  3. 4.3

    Intelligence-Driven Threat Hunting

    Raw data ≠ meaningful detection — intelligence provides direction. Focused hunts reduce wasted effort and blind spots, bring hunting in line with real-world threats (APT groups, malware campaigns), and support prioritization based on likelihood, relevance, and potential impact.

    Sources by level: strategic to tactical intel all matter, but prioritize technical and TTP-based indicators; sources include OSINT feeds, commercial feeds, sector ISACs/CISA alerts, and internal telemetry (previous IR cases, phishing reports).

    Building a hypothesis from intel: "If [actor/tool] targets organizations like ours, we might see [behavior] in [data source]." Example: "If Volt Typhoon is targeting ICS systems, are there WMI events in the Windows IT system logs?" This reinforces a proactive, analytical mindset.

    ATT&CK-based hunting: convert intel to behaviors via ATT&CK techniques. Benefits: TTP-based hunting scales better than IOC-based hunting, and produces reusable detection content across environments. Tools: ATT&CK Navigator, Unfetter, ThreatMapper.

    Visibility needed: Endpoints (EDR, logs, AV), Authentication (Windows Events, AD logs), Network (NetFlow data, proxy, DNS), Cloud (CloudTrail, GCP logs). Tool examples: Splunk, ELK, Velociraptor, Sigma rules, EQL.

    6-step hunting process:

    1. Ingest and contextualize threat intel

    2. Create a hypothesis from a relevant actor/tool

    3. Map to ATT&CK techniques

    4. Build hunt queries/detections

    5. Validate with real data

    6. Feed results into IR/SIEM/detection

    Worked example — TA551: Intel shows TA551 uses Excel macros → RDP → Cobalt Strike. Hypothesis: look for Excel spawning unusual child processes. TTP mapping: T1204.002 (User Execution), T1059.005 (VBScript), T1219 (Remote Access Software). Action: hunt EDR logs for excel.exe spawning powershell.exe, followed by outbound C2.

    After the hunt: refine detections & SIEM rules; share TTP observations with SOC/IR; feed context back into the TIP or wiki; update adversary playbooks or threat models.

    Traditional vs. intelligence-driven hunting:

    FeatureTraditionalIntelligence-Driven
    ScopeBroad, unfocusedScoped to threats
    DriversGut feeling, anomaliesAdversary behaviors, intel
    OutputsAlerts, anomaliesDetections, context, enrichment
    EfficiencyVariesHigh (targeted effort)

    Building repeatable workflows: templates for hypothesis generation, ATT&CK-mapped detection libraries, threat-actor tagging in logs, and integration with SOC/IR feedback loops so hunting is part of daily ops, not a side project.

    Threat Hunting Maturity for an organization: Level 1 — IOC-based reactive hunts; Level 2 — behaviorally focused TTP hunts; Level 3 — fully integrated, intelligence-driven, adversary-informed hunting cycles.

05

Sources, Standards & Collaborative Sharing

  1. 5.1

    Threat Intelligence Sources
    • OSINT (Open-Source Intelligence) — GitHub, Twitter/X, Reddit, VirusTotal, blogs, Pastebin, etc. Strengths: free and abundant, diverse (social media/public malware repos/blogs), real-time and community-driven. Weaknesses: high noise-to-signal ratio, often unauthenticated/unverified, susceptible to disinformation or manipulation.
    • Commercial Feeds — Mandiant, Recorded Future, Flashpoint, Palo Alto Unit 42, etc. Strengths: curated, enriched, usually vetted; often come with support or threat-actor tracking; SLAs and integrations with SIEM/TIP/SOAR. Weaknesses: expensive (may overlap with OSINT); risk of a "vendor echo chamber" where everyone shares the same indicators.
    • Closed Sources — government agencies, sector-specific ISACs. Strengths: highly exclusive (government intel, industry-specific trust groups, dark web infiltrations), can provide early warning or high-confidence intelligence. Weaknesses: hard to access (clearance, trust, vetting), little transparency into collection methods.

    The best intelligence comes from correlating across sources. Example: OSINT detects a new phishing domain → a commercial feed matches the infrastructure to a known APT → a closed source confirms campaign targeting via classified alerts.

    Evaluation questions: What's the source's collection methodology? Can it be actioned? Is it redundant or unique?

    Worked timeline comparison (a hypothetical December incident):

    • Dec 9 — OSINT: tweets leak an exploit, GitHub PoCs drop, Minecraft servers get tested (fast, noisy alerts; crowd-sourced awareness).
    • Dec 10 — Commercial feeds: YARA/Sigma rules released, initial TTP attribution, endpoint detection guidance (structured detections; context from experts).
    • Dec 11 — Closed sources: alerts to critical infrastructure organizations, early ransomware warnings, nation-state actor reports (strategic response; trusted sector coordination).

    "Speed + Structure + Strategy = Resilience."

    Strategic decisions: Build vs. Buy vs. Borrow; use TIPs and automation to reduce overload; create internal policies for validation and usage.

  2. 5.2

    STIX, TAXII & TLP
    • STIX (Structured Threat Information eXpression) is Structured (defined schema for consistency), Descriptive (captures indicators, actors, malware), Relational (links objects like "Malware used by Actor"), and Machine Readable (written in JSON for automated parsing).
    • TAXII (Trusted Automated eXchange of Indicator Information) is a Transport Protocol (moves STIX data between systems securely/reliably), a Standardized API (HTTP/S and RESTful endpoints), supports Push & Pull (push to subscribers or let consumers pull on demand), organizes intel via Collections & Channels (topic-based containers), and is Designed for Automation (machine-to-machine sharing in real time or on schedule).
    • TLP (Traffic Light Protocol) levels:
      • TLP:RED — for named recipients only; do not share.
      • TLP:AMBER — limited disclosure, only to those who need to know within your organization.
      • TLP:GREEN — share with peers and partners within your community.
      • TLP:CLEAR — no restrictions; may be shared publicly.

    How they relate: STIX provides the data format; TAXII provides the transport mechanism; TLP provides the handling and dissemination guidance. In short: STIX = what is shared, TAXII = how it's shared, TLP = who it's shared with.

  3. 5.3

    Structured Analytical Techniques & Cognitive Bias

    Structured Analytical Techniques (SATs) = formalized methods used to improve critical thinking and analysis. Purpose: examine assumptions, identify gaps and contradictions, minimize biases, consider alternative hypotheses.

    7 SATs, each addressing a different weak point in analysis:

    • Analysis of Competing Hypotheses (ACH) — a matrix-based technique for comparing multiple hypotheses against evidence to see which is most consistent.
    • Key Assumptions Check — a technique to identify and challenge the assumptions that underpin your analysis.
    • Red Team Analysis — analysts take on the role of the adversary to understand their objectives, constraints, and likely next moves.
    • Indicators and Signposts of Change — a method to monitor whether your hypothesis continues to be supported over time.
    • Timeline / Chronology Mapping — organizes events in time to find gaps, triggers, or patterns suggesting causality or coordinated activity.
    • Mind Mapping / Link Analysis — visually connects people, infrastructure, malware, behaviors, and events.
    • Devil's Advocacy — deliberately arguing against the prevailing analysis to find its weaknesses.

    Why SATs matter in CTI — they counter deception, confirmation bias, time pressure, and financial risk in the analysis process.

    7 cognitive biases that undermine intelligence analysis:

    BiasWhat it isWhy it mattersMitigation
    Confirmation BiasTendency to favor or interpret information that supports existing beliefsPoor attribution, blind spots, misidentification of TTPsAnalysis of Competing Hypotheses
    Anchoring BiasRelying too heavily on the first piece of information receivedSkews analysis toward viewing further evidence through that lensKey Assumptions Check
    Mirror ImagingAssuming the adversary thinks, prioritizes, or acts the way you mightFlawed threat modeling, misjudging adversary goals/tacticsRed Team Analysis
    Availability BiasReliance on recent, vivid, or easily recalled events instead of actual probability/relevanceOverweights recent/high-profile attacks, ignores broader trends and low-visibility threatsTimelines & Historical Analysis
    GroupthinkPressure to conform to consensus opinions within a team, suppressing dissentPrevents challenging flawed assessments, reduces creativity, can cause analytic failuresDevil's Advocacy or Structured Team Debate
    SatisficingStopping at the first "good enough" answer instead of exploring better explanationsShallow analysis, missed threatsIndicators and Signposts of Change
    OverconfidenceOverestimating the accuracy, completeness, or value of one's own analysisRigid assessments, poor stakeholder communication, disregard for new evidenceConfidence Rating Frameworks + Peer Review

    Key takeaways: SATs are tools for thinking critically under pressure; cognitive biases are hidden obstacles that can derail judgment; combining SATs with bias awareness builds more rigorous, transparent, and actionable threat intelligence.

  4. 5.4

    ISACs & Collaborative Sharing

    ISACs (Information Sharing and Analysis Centers) trace back to Presidential Decision Directive 63; they're non-profit, member-driven organizations focused on critical infrastructure protection. Major ISACs by sector: Financial, Healthcare, Energy, IT, Auto, Multi-State Government, Aviation.

    How threat data flows: ingested by cleared analysts, technical platforms, and real-time feeds; then data enrichment; then data redistribution.

    Bridging public and private sectors: enables rapid sharing of classified and unclassified cyber threat data, mutual coordination, and resilience/recovery support.

    Federal players: CISA, NSA Cybersecurity Directorate, FBI InfraGard, DoD/DC3, DOE/HHS/DOT/Treasury, USSS Electronic Crimes Task Force, USSS Cyber Fraud Task Forces.

    Mechanics of sharing: TLP labels control distribution, packaged as STIX, pushed/pulled via TAXII, integrated into SIEMs (Elastic, Splunk), TIPs (ThreatConnect, MISP, Anomali), and SOAR platforms.

    Real coordination examples:

    • SolarWinds (2020): NSA detected lateral movement; Microsoft and FireEye discovered the supply chain compromise; CISA coordinated disclosure and mitigation; a STIX package with SUNBURST IOCs was shared.
    • Colonial Pipeline (2021): FS-ISAC shared threat indicators related to DarkSide; MS-ISAC disseminated guidance to SLTT agencies; DHS/CISA coordinated private briefings for the utility sector.

    Getting started: join an ISAC relevant to your sector; set up automated sharing (configure TIPs with STIX/TAXII access, ingest MISP feeds into SIEMs); build relationships; share intelligence, not just consume it.

06

Real-World Case Studies

  1. 6.1

    SolarWinds (2020)

    Background: the SolarWinds Orion platform, used by thousands of organizations including the U.S. government, was compromised via a trojanized software update carrying the SUNBURST backdoor — discovered by FireEye in December 2020.

    Timeline: September 2019 — initial access. March 2020 — trojanized update deployed. December 2020 — discovery and public disclosure.

    Threat actor: a Russian SVR-linked group, previously associated with the 2016 DNC hack, known for stealthy espionage, long dwell time, and strong OPSEC.

    TTPs: supply chain compromise; SAML token forgery; use of native Windows tools (LOLBAS); C2 over HTTPS disguised as normal traffic.

    CTI across levels: Strategic — national security implications, vendor risk; Operational — tracking C2 infrastructure; Tactical — mapping TTPs to ATT&CK; Technical — IoCs (hashes, domains, URLs, certs).

    Collaborative response: FireEye, CISA, Microsoft, and Volexity cooperated; sharing happened via STIX/TAXII and GitHub repos; disclosure moved through TLP levels — TLP:RED → TLP:AMBER → TLP:WHITE — as confidence and readiness to share broadened.

    Lessons: CTI must include vendor trust models; detection requires telemetry beyond malware; attribution influences the public/private response.

  2. 6.2

    NotPetya (2017)

    Context & initial beliefs: in June 2017, a global attack initially thought to be ransomware — targeted Ukraine via compromised MeDoc accounting software, demanded a BTC ransom, but the decryption keys were non-functional.

    Technical reality: it was actually a wiper, not ransomware — exploited EternalBlue and EternalRomance, used Mimikatz for credential harvesting, and spread via PsExec for lateral movement.

    Attribution evolution: early confusion between ransomware and nation-state activity; later formal attribution to the Russian GRU (APT28/Sandworm); the actual target was destabilization of Ukraine and economic damage.

    What went wrong in response: the mistaken ransomware classification delayed a proper response; there was a lack of immediate cross-sector sharing; an overemphasis on the malware itself meant the strategic intent behind the attack was missed.

    CTI across levels: Strategic — nation-state cyberwarfare and deterrence; Operational — impact analysis across organizations; Tactical — lateral-movement techniques, propagation methods; Technical — IoCs and YARA rules.

    Impact: hit Maersk, FedEx (TNT Express), Merck, and Saint-Gobain, with over $10 billion in total damages. Highlight: Maersk rebuilt its entire Active Directory infrastructure from a single untouched domain controller that happened to be in Ghana.

    Lessons: attribution isn't just "whodunit" — it's about intent; CTI must continuously reassess the why of an attack; strategic and operational intel can't lag behind technical findings.

    Final course takeaways: CTI is dynamic — it must evolve with adversaries; attribution is a lens, not a conclusion; intelligence must be timely, shared, and multi-level; real-world CTI blends strategic insight with technical detail; collaboration is essential — no one organization sees the full picture.

Attackers & Motivations

  1. 1.1

    Threat Actors — Big Picture
    • External — no account or authorization on network / system. Range: unskilled attacker → well-funded nation-states.
    • Internal — has been granted some level of authorization. Employees, vendors, business partners, etc.
    • All attackers have some sort of motivation & intent: financial, political, curiosity, etc. Actions: data theft, vandalism, etc.
    • Various levels of skill, funding, and resources:
      • Unskilled using "commodity" malware and tools.
      • Custom zero-day exploits, with government funding.
  2. 1.2

    Nation-State Actors
    • Threat actor supported by resources of a host country — military, government, financial, etc.
    • Separated from host government / country:
      • Unofficial support.
      • Pose as "hacktivists" or independent groups, other countries.
      • Provides plausible deniability to government.
    • Frequently attack using APTs (Advanced Persistent Threat).
    • Motivations: espionage, financial, cyber "warfare", disinformation, other political.
  3. 1.3

    APTs
    • Highly sophisticated and capable of extended attacks.
    • Advanced — extensive skills & resources, capable of complex attacks.
    • Persistent — able to remain on the network long-term without detection.
    • Often sponsored by nation-states (officially or unofficially).
    • Often target high-value organizations — government agencies, critical infrastructure, political campaigns, etc. Smaller organizations may be targeted as part of a supply chain attack.
    • Motivations similar to nation-states.
  4. 1.4

    Organized Crime
    • Not necessarily tied to a specific country.
    • Very similar to typical organized crime syndicates — cyber attacks vs physical attacks.
    • May span multiple regions, jurisdictions — complicates prosecution.
    • Common goals are financial profit, carried out through financial fraud and extortion, and data exfiltration (especially PII / PHI & IP).
  5. 1.5

    Hacktivists
    • Groups of threat actors motivated by political and social causes — Anonymous, WikiLeaks.
    • Common goals / motivations:
      • Data theft with intention to release.
      • Defacement of public sites.
      • DoS (denial of service) attacks.
    • Often target political and financial groups. May also target media organizations and other companies. Targets depend solely on the group's goals.
  6. 1.6

    Others — Unskilled Attackers & Insider Threats
    • Unskilled attackers
      • Threat actors who may have minimal skills and knowledge.
      • Normally use commonly available tools and malware.
      • May not understand tools or tactics they are using.
      • Often have no specific target or goals — gaining attention, proving their skills & abilities.
    • Insider threats
      • Intentional
      • Unintentional
      • Shadow IT
02

Threat Vectors

  1. 2.1

    What Is an Attack Vector?
    • Path that an attacker takes to gain unauthorized access.
    • Common attack vectors:
      • Removable storage
      • Software / hardware vulnerabilities
      • Unsupported or out-of-date systems
      • Images and malicious files
      • Open ports
      • Supply chain
  2. 2.2

    Removable Storage
    • USB thumb drives, portable HDs, memory cards, (less frequently) CDs.
    • Attackers can conceal malware on removable media:
      • Run automatically when inserted.
      • Run when application on drive launched.
    • USB drop attack
      • Attackers place removable media around specific locations.
      • Relies on users picking up the drive and inserting out of curiosity.
    • Attacks may run automatically or require user action — if action required, social engineering to trick user.
  3. 2.3

    Malicious Files
    • One of the most common methods for spreading malware.
    • Malware can be embedded in legitimate files:
      • Weaponized applications.
      • Macros in Word documents & PDF files.
      • Steganography — concealing information within other messages, commonly used with image files.
    • Frequently combined with other vectors to deliver files — email delivery, removable storage.
  4. 2.4

    Messaging-Based Vectors
    • Email
      • One of the most common attack vectors.
      • Phishing emails, malicious attachments and links in the message body.
    • SMS
      • Frequently used to bypass MFA restrictions.
      • Can also compromise mobile devices — attackers send malicious links / files via SMS.
    • Instant Messaging
      • Similar to SMS, but available on more systems.
      • Typically more secure than SMS, but can still contain vulnerabilities.
    • Social engineering is the common thread among messaging vectors.
  5. 2.5

    Vulnerable & Unsupported Systems
    • Attackers frequently look for and exploit vulnerabilities. NIST definition: "Weakness in an information system, system security procedures, internal controls, or implementation that could be exploited or triggered by a threat source."
    • Vulnerabilities are very common in all systems — software & hardware.
      • Zero-day — new vulnerability that is being exploited, no fix yet.
    • Unsupported systems
      • Not actively maintained or supported by vendor / manufacturer.
      • Commonly do not receive security updates.
      • Contain multiple vulnerabilities and outdated security measures.
03

Advanced Malware

  1. 3.1

    Malware Classifications
    • Malware = software that does something bad, from the user perspective — malicious software.
    • Various classifications:
      • Virus, worms
      • Trojans
      • Ransomware
      • Potentially unwanted programs (PUPs)
      • Adware / spyware
      • Remote access trojan (RAT)
      • Rootkits
      • Logic bombs
  2. 3.2

    Ransomware
    • Malware that attempts to extort a victim for money to recover data:
      • Most will encrypt and only provide decryption after payment — crypto-ransomware.
      • Some is only threatening, without blocking access.
    • Will prominently display notice(s) demanding payment or other action.
    • Encryption-based can only be remediated by restoring data — possibly by paying ransom, but almost never recommended (sometimes illegal).
    • Demand payment via various methods, often cryptocurrency.
  3. 3.3

    Remote Access — RAT & C2
    • RAT — Remote Access Trojan
      • Remote Administration Tool.
      • Provides attacker with backdoor access to system.
    • Command & Control
      • Attacker-controlled infrastructure that compromised systems connect to.
      • C&C or C2.
      • Often use disguised DNS or HTTPS traffic to hide usage.
  4. 3.4

    Rootkits & Logic Bombs
    • Rootkit
      • Malware that can run as unrestricted system processes.
      • Can compromise critical system files and be difficult to detect — high level of access results in effective masking, difficult discovery.
      • Often erases logs to hide evidence of infection.
      • Modern OSes have mechanisms to help prevent.
    • Logic bomb
      • Malware designed to not run immediately.
      • Can wait for a predetermined date / time or specific event before executing.
      • Not necessarily typical malware — e.g., a disgruntled system admin leaving a scripted trap.

Forming a Hypothesis

  1. 5.1

    What a Hypothesis Is
    • Threat hunts start with a hypothesis — an assumption about malicious activity occurring, that can be tested. Examples:
      • "Threat actors have created scheduled tasks to execute code."
      • "An endpoint has communicated with <malicious IP>."
    • Identifies specific behavior / activity to hunt for.
    • Requires understanding of attack technique.
    • Indicates which data and sources used to detect threat.
    • Can be very specific or more vague.
  2. 5.2

    Four Steps to Build One

    1. Determine tactic / technique or IOC

      Review intelligence & other sources (MITRE ATT&CK).

    2. Identify associated procedure(s)

      MITRE ATT&CK as one source. Additional research recommended: prerequisites, other requirements, outcome of success, etc.

    3. Determine logs / data required for hunt

      Where do artifacts exist on systems? Files, registry, memory, network traffic, processes, etc.

    4. Set scope of hunt

      Systems involved, duration of hunt.

Structured Hunt — Worked Example

  1. 6.1

    Structured Hunt Overview
    • Hypothesis based on attacker's methods.
    • Relies heavily on TTPs — MITRE ATT&CK Matrix.
    • Hunt based on possible symptoms of that type of attack.
  2. 6.2

    Hypothesis Building — Create Account for Persistence
    • Tactic — Persistence
      • "Adversary is trying to maintain their foothold."
    • Technique — Create Account
      • Used to maintain access to system.
      • Can establish secondary access without needing persistence remote tools.

    Resulting hypothesis: "Attackers have created administrative accounts on endpoints to maintain their access on the network."

      • Any type of unusual protocol usage.

03

Capturing Network Traffic

  1. 3.1

    Network Sensor Basics
    • Can be individual devices or configurations on network devices.
    • Allows logging / capturing and analysis of traffic.
    • Placement in network determines logged traffic:
      • On switch — can see any traffic on that switch.
      • Between two routers — can see traffic between those devices.
    • Provide insight into exactly what is happening on the network — possible C2 activity, workstations downloading payloads, data exfiltration.
  2. 3.2

    Tap and Mirror
    • Network Tap
      • Usually standalone device (can be built-in to other devices).
      • IPS systems can use this to monitor / block traffic.
      • Three network ports:
        • Traffic between two ports passes through.
        • Traffic is copied and routed to monitor port for logging.
    • Port mirroring / SPAN
      • Configuration on network device.
      • One port set up as "mirror" port.
      • All traffic on device copied to that port for logging.
      • Can affect performance and result in dropped packets.
  3. 3.3

    Application Capture
    • Wireshark (or similar application).
    • Provide ability to capture packets on individual workstation:
      • Does not capture if workstation not source / destination — except broadcasts.
    • Encrypted traffic is captured — but still encrypted.
    • Can result in very large capture file — capture filters can reduce, but may miss important data.
  4. 3.4

    Linux — tcpdump Command Reference

    tcpdump [options] [filter expression]

    Example: sudo tcpdump -i eth0

    • --list-interfaces
    • -c
    • -w
    • Numerous capture filters.

Recognizing Abnormal DNS & HTTP/HTTPS

  1. 8.1

    DNS — Normal vs Suspicious
    • Typically a query-response protocol.
    • Normally uses UDP 53 — many legitimate uses for TCP 53.
    • Traffic destination should always be DNS servers.
    Normal DNS TrafficSuspicious DNS Traffic
    UDP 53TCP 53 (not always)
    Should only go to DNS ServersDNS traffic not going to DNS Servers
    Query → responseMultiple queries with no response
     Multiple responses, no queries
  2. 8.2

    HTTP — Normal vs Suspicious
    • HTTP traffic typically requests and responses — messages, responses include 3-digit status code (200, 302, 404, etc).
    • HTTP messages include message header and body.
    • Methods used to perform various operations — 9 current methods (GET, HEAD, PUT, POST, etc).
    • May be more difficult to spot malicious traffic.
    Normal HTTP TrafficSuspicious HTTP Traffic
    Port 80, TCPPort 8080, TCP
     Port 8088, TCP
     Other, non-standard ports
     Standard ports may still be used by attackers
    Normally not blocked on networks 
    Plaintext traffic (NOT HTTPS)Encrypted traffic on port 80 or using HTTP
    FQDN connection to serverIP connection to server (especially external IPs)
  3. 8.3

    HTTPS
    • Similar to HTTP, but encrypted.
    • Handshake between client & server prior to communication:
      • Agree on protocol version.
      • Cryptographic algorithms selected.
      • Optional mutual authentication.
    • Attackers commonly use standard HTTPS ports (443, 8443, etc).
    • Non-encrypted traffic on 443 should be suspicious.
    • Normally, data exchanged cannot be read — may be able to decrypt with Wireshark or other tools.

03

Windows Services & Scheduled Tasks

  1. 3.1

    Windows Services
    • Processes running in background.
    • Multiple ways of starting:
      • On boot (automatic).
      • Manually by user or trigger.
    • Used by attackers for persistence — malicious process to start at boot, connect to C2 infrastructure, ensure elevated access.
  2. 3.2

    Service Attacker Abuse
    • Create new service:
      • sc.exe create
      • PowerShell New-Service
      • WMI commands
      • Registry modifications — HKLM\SYSTEM\CurrentControlSet\Services\
      • Third-party tools
    • Modify / replace existing service — change executable.
    • Change recovery options on service — run program when service fails.
  3. 3.3

    Recognizing Malicious Services
    • Any application can create a service.
    • Service creation indicators:
      • sc.exe create in logs.
      • New-Service in logs.
      • reg add in HKLM\SYSTEM\CurrentControlSet\Services\ — Sysmon Event ID 12, 13, 14 (RegistryEvent).
      • Event ID 4697 or 7045.
    • Unrecognized / unauthorized users creating / modifying services.
  4. 3.4

    Scheduled Tasks
    • Automated tasks to run programs or scripts.
    • Multiple triggers:
      • Date / time
      • Regular intervals (ex: every 2 weeks)
      • At log on, start up
      • Workstation lock / unlock
    • Frequently used by attackers for persistence and stealth.
  5. 3.5

    Task Attacker Abuse
    • Malicious task creation:
      • Command line: schtasks /create
      • PowerShell: New-ScheduledTask
      • GUI: Task Scheduler — can be harder to detect in hunts.
    • Modify existing tasks:
      • schtasks /change
      • Set-ScheduledTask
    • If using PowerShell, command may be encoded.
  6. 3.6

    Recognizing Malicious Tasks
    • Task creation indicators:
      • schtasks /create
      • New-ScheduledTask
      • Event ID 4698 — Scheduled Task Created.
      • Event ID 4700 — Scheduled Task Enabled.
      • Event ID 106 — Scheduled Task Created (in Task Scheduler channel).
    • Task modification indicators:
      • schtasks /change
      • Set-ScheduledTask
      • Event ID 4702 && 140 — Scheduled Task Updated.

Sysmon

  1. 4.1

    What Is Sysmon?
    • Part of Sysinternals suite.
    • Monitors system and logs activity to Windows event log — additional logging not built in to Windows: file creation, network connections.
    • Operates as Windows system service / device driver — runs as protected process.
    • Should be installed on all endpoints as necessary — some data not logged by default Windows Events.
    • Logged events (ideally) forwarded to SIEM.
  2. 4.2

    • Logs process creation with full commands entered — includes current and parent process.
    • Records hash of executed files — multiple algorithms.
    • Logs driver and DLL loading with signatures and hashes.
    • Can log network connections — source process, IP address, port number, hostname.
    • File creation / overwrite information — including changes in file creation timestamp.

Splunk — Intro, SPL & Queries

  1. 5.1

    What Is Splunk?
    • Security Information & Event Management (SIEM).
    • Log / data analysis.
    • Collects logs from multiple sources — aggregation and correlation.
    • Capable of real-time analysis and alerting.
    • Dashboards & visualizations.
    • Raw log searches (SPL).
    • Add-on applications to extend functionality.

    Splunk Architecture: Forwarder(s) → Indexer → Search Head.

  2. 5.2

    Splunk Processing Language (SPL)
    • Index
    • Sourcetype
    • Filters
    • Pipes
    • Commands: table, stats, sort, top, dedup
    • Field=value
    • Boolean logic & grouping
    • Raw event search vs transforming search
  3. 5.3

    Building a Query
    • Good queries start with good hypotheses — know what you're looking for.
    • Example: "Attackers are running suspicious scripts from temporary folders."
      • Search possibilities:
        • .ps1 files executed within scope timeframe.
        • Any non-executable from C:\Windows\Temp or C:\Temp.
        • Script files created in temp folders.
  4. 5.4

    Common Query Purposes
    • New user creation.
    • Brute force attempts.
    • Unexpected outbound network connections.
    • Suspicious PowerShell activity — encoded commands, downloads.
    • Looking for persistence techniques — scheduled tasks, autorun, malicious services.
  5. 5.5

    Splunk Search Tips
    • Ensure proper time range is appropriate for hunt.
    • Format results into tables for easier readability — useful for summary of information.
    • Use stats, count, sort, top & rare.
    • Remember | to add functionality:
      • where — filters results further.
      • eval — rename fields, create new fields based on calculations.

Threat Hunting with Splunk — Worked Hunt

  1. 6.1

    Putting It All Together
    • Threat hunting is proactive — not relying on alerts or notifications.
    • Hypothesis-driven — not random queries.
    • Using Splunk in hunts:
      • Centralized visibility with historical data.
      • Ability to easily pivot searches, aggregate data, visualize query results.
  2. 6.2

    Worked Hunt — Obfuscated PowerShell Downloader

    Hypothesis: "An attacker has used PowerShell to download malware using obfuscated or encoded commands."

    1. Identify relevant logs

      Windows Event Logs; Sysmon logs; Network data (DNS, firewall, etc).

    2. Execute initial queries

      Use the correct index(es). Example: index=sysmon EventCode=1 Image="*powershell*" CommandLine="*enc*". Analyze results to determine next steps.

    3. Pivot as necessary

    Additional queries used during the pivot:

    • index=sysmon EventCode=1 Image="*powershell*" CommandLine="*update.ps1*"
    • index=wineventlog EventCode=4688 New_Process_Name="*powershell*" Command_Line="*update.ps1*"
    • index=sysmon EventCode=1 CommandLine="*update.ps1*" | table _time, Computer, Image, CommandLine, Hashes
    • index=sysmon EventCode=1 Hashes="*<hash>*" | table _time, Computer, Image, CommandLine, User, Hashes

    Best Practices: remember indexes; ensure time range is correct; include sourcetype if known (reduces scope of search); use fields when searching (Image="*powershell*"); wildcards only when needed (can affect performance).

ELK — Intro, Search Languages & Queries

  1. 7.1

    What Is ELK?
    • Three components working together:
      • Elasticsearch — search and analytics.
      • Logstash — data processing and transformation.
      • Kibana — visualization and dashboards.
    • Often includes Beats (Winlogbeat / Filebeat) — used for shipping log files.
    • Similar uses and functionality to Splunk — visualizations and real-time searches.

    ELK Architecture: Winlogbeat / Filebeat → Logstash → Elasticsearch → Kibana.

  2. 7.2

    Searching in ELK — KQL & EQL
    • ELK supports multiple query languages.
    • KQL — Kibana Query Language
      • Faster, simpler queries.
      • Field-based matches.
    • EQL — Elasticsearch Query Language
      • Event correlation.
      • Sequences (multi-step searches).
  3. 7.3

    KQL Details
    • Field-based searching — : equals.
    • Boolean logic — AND, OR, NOT.
    • Wildcards.
    • Field selection for ad hoc filters.
    • Best practices:
      • Field-based searches instead of full-text.
      • Save commonly used queries.
  4. 7.4

    EQL Details
    • Excels at searching multi-step events / attacks.
    • Simple query:
      • event_type where condition
      • process where process.name == "powershell.exe"
    • Logical operators: ==, !=, <, >, and, or, not.
    • Sequences: "This happened, then that happened."
  5. 7.5

    Common ELK Queries
    • Suspicious account logins.
    • Suspicious process behavior.
    • Unexpected outbound network connections.
    • Suspicious PowerShell activity — encoded commands, downloads.
    • Looking for persistence techniques — scheduled tasks, malicious services.
